Transactional key-value storage for DSON

defuss-dbsonl runs on Node.js, Bun and in dedicated browser workers. Batches and transactions publish all of their changes or none, snapshots keep reading the state they opened on, and several processes or workers can share one database.

* The demos run the packaged library in your tab. Three use memory storage; one keeps a counter in your browser's origin private file system (OPFS).

What you get

Values keep their types

Values are stored as DSON, typed JSON from defuss-dson: Map, Set, Date, RegExp, bigint, typed arrays, undefined, NaN and cyclic references come back as they went in. JSON turns a Map into {} and a date into a string, and throws on a bigint.

Readers never block writers

A snapshot pins one immutable root of the tree. Commits keep publishing while it reads, and it sees none of them until you open a new one.

All changes or none

A batch or a transaction becomes visible as one revision. A transaction fails with CONFLICT when any other commit published after its snapshot, which rules out write skew.

Opens fast, however much it holds

A log-based store replays its log on open, so startup slows as data grows. defuss-dbsonl reads a small header that points at the current tree, not the stored data; the benchmark reopened a database in 0.52 ms on Node.js. Memory is capped by the page cache budget, not by the number of keys.

Shared by processes and tabs

Servers coordinate through kernel file locks, browser workers through Web Locks. A process that dies releases its locks, and no lock expires on a timer, so a paused writer never loses ownership.

Corruption fails closed

Every frame carries a CRC32C checksum, and verify() walks every reachable value and index page. Nothing repairs data by guessing, because a guessed repair can turn damage into silent data loss.

Where it fits

The storage and API layer for defuss-dataview

defuss-dbsonl is designed as the backing store and API of defuss-dataview. It turns the byte I/O of defuss-storage into a transactional key-value store and encodes every value with defuss-dson.

Optimistic concurrency, no silent retry

Transaction A reads visits and waits. Writer B commits in between. When A publishes, its snapshot is stale, so it fails with CONFLICT. The library does not retry, because a retry would run your callback and its side effects again.

    Building blocks

    Six parts, one store

    Copy-on-write B+tree

    Fanout 32. A commit rewrites the path from leaf to root and never changes a written page.

    Immutable roots

    Every revision is a root. A snapshot pins one and reads it while new roots are published.

    Two head slots

    Two checksummed 4 KiB slots name the current root. Writers alternate between them; the newest valid slot wins.

    DSON frames

    Values and index pages are DSON frames with a length, a header CRC32C and a payload CRC32C.

    Bounded page cache

    Decoded index pages stay in an LRU cache limited by bytes and page count. Values are always read fresh.

    Lock order

    Commit lock, then generation pin, then I/O lock. Kernel locks on servers, Web Locks in browsers, no timeouts.

    How it works

    One commit, crash-safe at every step

    A commit writes next to the old data, never over it, and switches with one small write at the end.

    Design choices

    What each choice costs

    Each card names the design in use, the obvious alternative, why the alternative lost and what the choice costs.

    Finding keys

    Persistent B+tree with fanout 32 and a bounded page cache

    Instead of an in-memory key map rebuilt from a log

    Why
    Memory does not grow with the number of keys, and opening needs no replay.
    Cost
    A point read whose page is not cached reads from disk.

    Readers and writers

    Immutable roots, pinned per snapshot

    Instead of read locks that block commits

    Why
    A slow reader cannot stall a writer.
    Cost
    Old generations stay on disk until their readers close.

    Atomic publication

    Two checksummed head slots, written alternately

    Instead of writing a new file, then renaming it

    Why
    OPFS and Storage offer no uniform atomic rename.
    Cost
    Every commit writes one 4 KiB slot.

    Several writers

    OS whole-file locks or Web Locks, held per commit

    Instead of one process that owns the database

    Why
    Independent processes and workers share one database.
    Cost
    Commits serialize, so revisions keep a single order.

    Transactions

    One revision check for the whole database

    Instead of per-key conflict detection

    Why
    It rules out write skew and range phantoms without tracking read sets.
    Cost
    Writers on disjoint keys can still conflict.

    Space reuse

    Explicit compact() and collect()

    Instead of in-place updates or a background vacuum

    Why
    No hidden I/O: the application decides when to pay.
    Cost
    Compaction needs disk space for one live copy.

    Stale locks

    Kernel locks, released when a process dies

    Instead of lock files that expire after a timeout

    Why
    A paused process never loses ownership to a second writer.
    Cost
    Servers need the native lock addon.

    Contract

    Guarantees

    • All or nothing

      A batch or transaction becomes visible at once, as one revision, or not at all.

    • Serializable transactions

      A transaction commits only if no other commit published after its snapshot; otherwise it fails with CONFLICT instead of running your callback again.

    • Stable snapshots

      A snapshot reads the same root until you close it, while writers keep committing.

    • Flushed before published

      Values and index pages reach the device before a head slot points at them. On servers, directory metadata is synced too.

    • Crash-safe heads

      Two checksummed slots survive an interrupted write of either one. A writer reuses the unpublished tail of a failed commit.

    • Fails closed

      Corrupt published data fails its checksum or verify(); nothing is repaired by guessing.

    • Locks without timeouts

      Kernel locks and Web Locks are released when their process or worker ends, never by a clock.

    The platforms these guarantees were tested on, and the ones they were not, are listed in the README.

    Get started

    Setup

    The package needs Node.js 20.19 or newer, Bun, or a dedicated worker in a browser with OPFS and Web Locks.

    bun add defuss-dbsonl

    The /server entry adds kernel file locks and directory sync. Every process that opens the same directory joins the same lock protocol.

    import { openDbsonl } from 'defuss-dbsonl';
    import { createFileBackend } from 'defuss-dbsonl/server';
    const db = await openDbsonl(await createFileBackend('./data'), 'orders', { create: true });
    await db.batch([
      { operation: 'put', key: 'order:1', value: { placed: new Date(), total: 4200n } },
      { operation: 'delete', key: 'cart:1' },
    ]);
    await db.close();

    OPFS grants synchronous access handles only to dedicated workers, so the database runs in one. Every worker that reaches the same files must use the same namespace, because the namespace names their shared Web Locks.

    import { createOPFSStorage } from 'defuss-storage/opfs';
    import { createBrowserBackend } from 'defuss-dbsonl/browser';
    import { openDbsonl } from 'defuss-dbsonl';
    const storage = await createOPFSStorage({ name: 'my-app' });
    const backend = createBrowserBackend(storage, 'my-app', navigator.locks);
    const db = await openDbsonl(backend, 'documents', { create: true });
    await db.put('hello', { bytes: new Uint8Array([42]), time: new Date() });

    Memory storage needs no platform entry. Clients coordinate only when they share the same backend object, which suits tests and short-lived caches.

    import { createMemoryBackend, openDbsonl } from 'defuss-dbsonl';
    const db = await openDbsonl(createMemoryBackend(), 'example', { create: true });
    const snapshot = await db.beginRead();
    for await (const row of snapshot.scan({ gte: 'a', lt: 'n' })) console.log(row.key);
    await snapshot.close();
